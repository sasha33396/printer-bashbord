# Первичный анализ проекта — 18 октября 2026

Анализ выполнен по локальной папке `printer-bashbord-Interactive_map`.
Рабочий сервер и данные на нём не проверялись.

## Устройство приложения

| Часть | Реализация |
|---|---|
| Интерфейс | React 18, Vite 5, Ant Design 5, React Router 6, Axios |
| Сервер | FastAPI 0.111, Pydantic 2.7, SQLAlchemy 2.0, Uvicorn |
| Хранение | SQLite, путь задаётся `DATABASE_URL` |
| Авторизация | Одна администраторская учётная запись из окружения, JWT на 8 часов |
| Развёртывание | Docker Compose: API на 8000, Nginx с интерфейсом на 3000 |
| Файлы | Фото и подложки в `PHOTO_DIRECTORY`, счета ремонтов в отдельном каталоге |
| Интеграции | XLSX/ZIP-импорт и экспорт, HTTP-счётчик Kyocera, сборщик OCS + AD |

Основные страницы подключены в `frontend/src/App.jsx`; актуальные страницы
расположены в подпапках `frontend/src/pages`. Рядом есть старые плоские файлы
страниц (например, `Devices.jsx`, `Login.jsx`): при изменении интерфейса следует
ориентироваться на импорты в `App.jsx`.

`backend/main.py` регистрирует маршруты и при импорте создаёт/обновляет схему,
пересчитывает разницы счётчиков ремонтов, инициализирует историю оборудования.
Миграции реализованы собственными SQL-операциями в `database.py` и
`schema_migrations.py`, отдельного Alembic-процесса нет.

## Основные связи данных

- Филиал → отделы → сотрудники и устройства.
- Рабочее место → сотрудник → текущие и исторические назначения складских активов.
- Складская позиция → поступления/выдачи; остаток рассчитывается по движениям.
- Поштучный картридж → складская карточка → состояние, держатель, устройство и слот.
- Устройство → ремонты, выполненные работы и расход материалов.
- Здание → этаж → геометрия и отметки объектов. Отметки ссылаются на карточки,
  оборудование может наследовать положение рабочего места или устройства.
- ЭЦП и МЧД хранятся в самостоятельных реестрах; сроки вычисляются на сервере.
- Общий журнал хранит события и исторические значения назначения оборудования.

Для тестирования нужна связанная база: одних справочников или случайных строк
недостаточно. Назначения должны согласовываться с местом, сотрудником и остатком;
номера оборудования должны быть уникальны между устройствами и складом;
картридж занимает один слот устройства; отметки карты должны относиться к своему
филиалу. В демобазе эти сценарии связаны, а новые тесты проверяют их через API.

## Что подготовлено

Генератор отдельной тестовой базы `backend/seed_demo.py`,
локальный запуск `start-demo.cmd` / `start-demo.ps1` / `tools/run_demo.py`, отдельная Docker-конфигурация,
проверки демоданных и [инструкция с ручными сценариями](demo.md).

Для локального Vite добавлена переменная `VITE_API_PROXY_TARGET`: тестовый стенд
направляет запросы к `127.0.0.1:8001`. Без неё остаётся прежний адрес `api:8000`.
В репозитории есть `frontend/package-lock.json`, позволяющий устанавливать зависимости через
`npm ci` воспроизводимо.

При прогоне на Windows найдены незакрытые SQLite-соединения: контекстный менеджер
`sqlite3.Connection` завершает транзакцию, но сам не закрывает файл. Исправлено
явное закрытие соединений в существующих тестах и в создании резервной копии
`reset_inventory_numbers.py`. Это устраняет ошибки удаления временных баз и
оставшийся открытым файл резервной копии на Windows.

## Наблюдения для дальнейшей работы

1. Для реального развёртывания обязательны непустые `ADMIN_LOGIN`,
   `ADMIN_PASSWORD`, `SECRET_KEY`. Сейчас в коде авторизации есть запасные
   значения `admin/admin` и `change-me-in-production`; отдельной системы ролей нет.
2. До обновления рабочего сервера нужен полный бэкап SQLite и каталогов файлов.
   ZIP-экспорт по инвентарным номерам не является полным бэкапом: он исключает
   ненумерованное оборудование и другие части данных.
3. Рабочий Dockerfile API запускает Uvicorn без `--reload`; режим наблюдения
   за файлами не используется в контейнере сервера.
4. Основная сборка интерфейса выдаёт предупреждение о большом JS-файле
   (около 2 МБ до gzip). Разделение страниц через lazy import может уменьшить
   первоначальную загрузку; сборку это предупреждение не блокирует.
5. Прямой `npm run dev` использует Docker-имя `api` по умолчанию. Для запуска
   без Docker теперь можно передать `VITE_API_PROXY_TARGET`; демоскрипт делает это.
6. Первоначально локальная папка была без `.git`. После проверки контроля версий
   настроены переносимый Git, ветка `Interactive_map` с исходной историей GitHub,
   локальная контрольная точка и отдельные резервные копии данных.
   Порядок восстановления: [Контроль версий](version-control.md).

Это первичный обзор архитектуры и запуска, а не полный аудит всех функций
или зависимостей. Изменение авторизации, миграций и рабочей Docker-конфигурации
не входило в подготовку демобазы.

- Сборщик OCS/AD: **25 тестов пройдено**; внешние OCS/AD не подключались.
- Frontend: **33 теста пройдено**, `npm run build` завершился успешно.
- Готовый файл SQLite: `integrity_check`, `foreign_key_check` и согласованность
  дат последней операции картриджа с журналом прошли.
- В реальном headless Edge проверены вход через форму и загрузка 11 разделов
  с демобазой: обзор, принтеры, склад, рабочие места, карты, ремонты, аналитика,
  оба реестра документов, история, настройки. Ошибок JavaScript и ответов API
  с кодом 400+ в этом сценарии нет. Карта отображается; сохранён скриншот
  `.cache/demo/map-preview.png` и отчёт `.cache/demo/browser-check.json`.
- Сквозной запрос через Vite → FastAPI проверен с реальной авторизацией.
- Docker Compose: YAML и изоляция ресурсов проверены; сборка контейнеров
  и их запуск не проверены из-за отсутствия Docker в текущем окружении.

замена с ресурсом 500 страниц, снятие с ресурсом 300 страниц, отмена удаления,
подтверждённое удаление из карточки и удаление из таблицы. JavaScript-ошибок
и ответов API с кодом 400+ в этих сценариях нет. Отчёт и снимок интерфейса:
`.cache/cartridge-browser/results.json`, `.cache/cartridge-browser/cartridge-resource.png`.
