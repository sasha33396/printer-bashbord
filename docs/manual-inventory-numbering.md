# Ручная маркировка оборудования

Новые и существующие карточки могут иметь пустой инвентарный номер. Номер вводится
с физической наклейки в формате `1-00001`; проверяется уникальность среди всех
карточек, включая архив. Перезапуск API, Excel-импорт и OCS-импорт не присваивают номера.
Миграция разрешает NULL у печатающей техники, сохраняя ID, ремонты, расходники и индексы.
Само обновление приложения сохраняет все имеющиеся номера.

## Выбрать сохраняемые номера

Создайте собственный список по образцу `backend/inventory_numbers_keep.example.json`.
Пример содержит вымышленные записи; замените их на проверенные наклейки своего
оборудования. Локальный файл `backend/inventory_numbers_keep.json` исключён из Git.
Путь к списку всегда передаётся явно через `--keep`.

Скрипт проверяет текущий номер, категорию и серийник. Для карточек без
серийника проверяет имя без учёта регистра. Отсутствие карточки, несовпадение или
дубли номеров останавливают операцию. Он не переносит указанные номера на другие карточки.

## Обновление и предварительная проверка на сервере

Перед обновлением сохраните актуальный бэкап БД и поместите свой список в каталог
данных API, смонтированный как `/app/data/inventory_numbers_keep.json`. Из `/opt/printer-bashbord`:

```bash
git pull --ff-only
sudo docker compose up -d --build api frontend
sudo docker compose exec -T api python reset_inventory_numbers.py --keep /app/data/inventory_numbers_keep.json
```

Последняя команда работает в режиме `dry-run`: рабочую БД и фотографии не меняет.
Она печатает строки `KEEP` для выбранных карточек, количество очищаемых номеров и путь отчёта.
При несовпадении серийника следует проверить физическое оборудование и запись
в списке, затем повторить проверку. Не удалять запись из списка ради обхода ошибки.

## Применение

Во время очистки API должен быть остановлен; сборщик OCS/AD и операции с фото
не должны выполняться. Скрипт запускается отдельным контейнером с теми же томами:

```bash
sudo docker compose stop api
sudo docker compose run --rm --no-deps api python reset_inventory_numbers.py --keep /app/data/inventory_numbers_keep.json --apply
```

При успехе будут `status: applied`, число сохранённых карточек и количество очищенных номеров.
При ошибке БД и перемещённые альбомы откатываются. Если скрипт завершился ошибкой,
проверить сообщение и отчёт перед повторным применением. API можно запустить вновь:

```bash
sudo docker compose up -d api
sudo docker compose restart frontend
```

Текущие номера очищаются у печатающей техники и складских карточек, включая архив,
кроме проверенных исключений из вашего списка. Сотрудники, оборудование, остатки, ремонты,
рабочие места, закрепления и связи OCS сохраняются. Старые номера остаются в
исторических снимках; в журнал добавляется событие очистки каждой карточки.
Повторное применение не создаёт повторных событий для уже очищенных номеров.

## Бэкапы и фотографии

Перед очисткой создаются `before.db` и `photos-before.tar.gz`, а `report.json`
содержит полный список прежних номеров и соответствующих карточек/альбомов.
Папка запуска: `/app/data/inventory-reset/<UTC-время>-<идентификатор>/` в томе БД.
Для копирования отчётов и бэкапов на сервер:

```bash
mkdir -p backups
sudo docker cp printer_api:/app/data/inventory-reset backups/
```

Фото очищаемой карточки переносятся в `unassigned-device-ID` или
`unassigned-warehouse_item-ID`. Содержимое, контрольные суммы и выбранное фото
рабочего места сохраняются. При последующем вводе номера альбом переносится в
папку этого номера. Освобождённый номер не показывает фотографии прежнего владельца.
Коллизия папок или символьная ссылка приводит к остановке.

Сбой питания/принудительное завершение между операциями с файлами и фиксацией БД
требует проверки `report.json`: БД и файловая система не являются одной транзакцией.
Для восстановления перед очисткой сохранены полный файл БД и архив фотографий.

ZIP-экспорт «по инв. №» содержит только карточки с заполненными номерами.
Для полного бэкапа всегда сохраняются БД и каталог фотографий.
