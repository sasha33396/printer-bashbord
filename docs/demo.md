# Необязательный тестовый стенд

Демонстрационные данные создаются только по явному запуску демостенда или генератора.
Готовых баз в репозитории нет. Обычный `docker compose up` создаёт пустую рабочую базу.
Получать рабочие данные или менять рабочий `.env` для тестирования не требуется.

## Запуск на этом компьютере

В PowerShell из корня проекта:

```powershell
.\start-demo.cmd
```

Скрипт открывает браузер после готовности обоих сервисов. Для запуска без открытия
браузера: `.\start-demo.cmd --no-browser`. Вариант `start-demo.ps1 -NoBrowser`
также доступен, если политика PowerShell разрешает выполнение скриптов.
Прямой запуск без обоих сценариев:

```powershell
.\.cache\runtime\python\python.exe tools\run_demo.py
```

- Интерфейс: **http://127.0.0.1:3001**.
- Документация API: **http://127.0.0.1:8001/docs**.
- Логин: **`demo`**.
- Пароль: **`demo-printer-2026`**.
- Остановка: **Ctrl+C** в терминале запуска.

На этом компьютере переносимые Python 3.12.10 и Node.js 22.17.0 подготовлены
в `.cache/runtime`, зависимости установлены. Они локальные и не входят в Git.
Скрипт использует `.venv/Scripts/python.exe`, переносимый Python или установленный
`python`; Node.js ищет в PATH и в подготовленном `.cache/runtime`.

При первом запуске создаётся рабочая демобаза
`.cache/demo/printer_dashboard.db`. Следующие запуски сохраняют изменения.
Фотографии, подложки планов, PDF-счета и логи также хранятся в `.cache/demo`.
Существующий файл без метки демобазы запуск не принимает. Порты 3001 и 8001
должны быть свободны; оба сервиса доступны только с этого компьютера.

## Запуск на другом компьютере без Docker

Нужны Python 3.12 и Node.js 20+ с npm. В корне проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
Push-Location frontend
npm ci
Pop-Location
.\start-demo.cmd
```

На Linux/macOS после установки тех же зависимостей:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
(cd frontend && npm ci)
.venv/bin/python tools/run_demo.py
```

## Запуск через Docker

Нужен установленный и запущенный Docker с Compose v2:

```bash
docker compose -f docker-compose.demo.yml up --build -d
```

Адреса и учётные данные те же. Это самостоятельная конфигурация с именем проекта
`printer-dashboard-demo`. Не объединяйте её с рабочим `docker-compose.yml`.
Параметры API заданы отдельно от рабочего `.env`; конфигурация не использует имена контейнеров `printer_api` /
`printer_frontend` и хранит данные в собственных томах `demo_db` и `demo_photos`.
Демобаза создаётся при первом запуске API; повторный запуск не заполняет её заново.

Просмотр логов и остановка с сохранением данных:

```bash
docker compose -f docker-compose.demo.yml logs --tail=100 api
docker compose -f docker-compose.demo.yml down
```

Для создания ещё одного чистого стенда без удаления первого:

```bash
docker compose -p printer-dashboard-demo-fresh -f docker-compose.demo.yml up --build -d
```

Предыдущий стенд следует остановить, чтобы освободить порты. Томам задаётся новое
имя проекта, поэтому предыдущая демобаза сохраняется.
Docker-конфигурация в текущей среде проверена статически; контейнеры здесь
не запускались, поскольку Docker не установлен.

## Создать отдельный файл SQLite

Файл SQLite можно сгенерировать и хранить отдельно от исходников. Его можно открыть
в просмотрщике SQLite или скопировать в отдельное тестовое окружение.
Логин и пароль хранятся в переменных окружения API, а не в SQLite.
Для входа задайте `ADMIN_LOGIN` и `ADMIN_PASSWORD`.

Автоматический локальный и Docker-запуск создают такие же сценарии относительно
даты первого запуска. Это позволяет проверить сроки ЭЦП и МЧД и спустя время.
Дальше даты в сохранённой базе естественным образом стареют.

Генерация нового отдельного файла с актуальными датами:

```bash
python backend/seed_demo.py --output .cache/demo-extra/printer_dashboard.db
```

Для воспроизводимого снимка можно добавить `--as-of 2026-10-18`.
Без `--output` файл создаётся в `.cache/demo/printer_dashboard.db`.
Любые SQLite-базы исключены из Git, включая созданные вручную в других каталогах.
Скрипт **не перезаписывает существующие файлы**, не использует `DATABASE_URL`
для выбора файла назначения и не добавляет тестовые записи в существующую базу.
`--if-missing` допускает повторное использование только помеченной демобазы
поддерживаемой версии. Перед сохранением проверяются целостность и внешние ключи.

У картриджа `1-00306` задан просроченный срок возврата; у `1-00305` и `1-00306`
есть измеренный цикл на 2 000 страниц. Установленные демокартриджи содержат
начальное показание счётчика. Для записей с пропущенными показаниями ресурс
остаётся неизвестным.

Для проверки сети включите «Карта сети» на первом этаже административного корпуса,
найдите «ДЕМО — компьютер» и нажмите «Показать цепочку». Путь проходит через
парные порты патч-панели и коммутатор до маршрутизатора на втором этаже.
Принтер и точка Wi-Fi подключены к другим портам коммутатора.
Новая схема входит во вновь создаваемые демобазы. Уже используемые
демобазы не заполняются повторно: после обновления в них сеть изначально пуста.
Инструменты редактора описаны в [инструкции по карте](maps.md).

ФИО и организации вымышлены, email и ссылки используют `example.test`.
IP устройств заданы из документальных диапазонов `192.0.2.0/24` и
`198.51.100.0/24`. Опрос физического принтера в этой базе не демонстрируется:
его IP требуется заменить на доступный тестовый принтер. Также нет готовых
фотографий, растровых подложек, PDF-счетов и реального подключения к OCS/AD;
загрузку файлов можно проверить вручную.

## Что проверить вручную

1. Откройте обзор, затем списки принтеров и склада. Проверьте поиск, сочетание
   фильтров, карточки, позиции без инвентарного номера и архив склада.
2. Откройте `ДЕМО-РМ-001`: сотрудник, компьютер, монитор и история назначения.
   Снимите оборудование на склад и назначьте резервное; проверьте историю.
3. На карте найдите сотрудника Иванова и его рабочее место. Оборудование
   наследует положение рабочего места. Переключите этаж, измените подпись комнаты,
   сохраните и обновите страницу.
4. В картриджах установите `1-00301` вместо `1-00303` в устройство `1-00001`
   (получатель — ИТ-отдел, слот `black`). Снятый картридж станет пустым.
   Отправьте его на заправку и верните; проверьте историю.
5. Откройте ремонты устройства `1-00001`: между двумя завершёнными ремонтами
   есть разница счётчиков 15 000 страниц. Текущий ремонт завершайте с ручным
   счётчиком, поскольку тестовый IP не связан с физическим принтером.
6. Проверьте оба реестра документов, сроки и архив; создайте новую запись.
7. Загрузите собственную тестовую фотографию оборудования, подложку карты или
   PDF-счёт, затем перезапустите стенд и проверьте сохранность файлов и записей.

Для новой локальной демобазы остановите стенд и **переименуйте**
`.cache/demo` (например, в `.cache/demo-saved-2026-10-18`). При следующем запуске
появится новая демобаза. Предыдущая база останется в переименованном каталоге.

## Автоматические проверки

```bash
cd backend
python -m unittest discover -s tests
cd ..
python -m unittest discover -s tools/ocs_ad/tests
cd frontend
npm test
npm run build
```

Новые проверки `backend/tests/test_demo_seed.py` создают собственные временные
базы и проверяют запрет перезаписи, сохранность посторонней базы, миграции,
сериализацию API, связи, остатки, сохранение планов и замену картриджа.
