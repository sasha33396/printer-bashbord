# Импорт компьютеров, ноутбуков, мониторов и сотрудников из OCS + Active Directory

## Статус

Backend и Python-сборщик подготовлены в ветке `feature/ocs-ad-import`. Сборщик запускается на Windows через CLI и читает AD с помощью PowerShell ActiveDirectory. [Инструкция запуска](../tools/ocs_ad/README.md). Интерфейс запуска импорта в приложении пока не реализован.

Первоначальный источник XML сетевого сканирования заменён REST API OCS Inventory. Филиал/склад и отдел при импорте необязательны. AD используется для проверки пользователя и получения имени, а не для определения филиала: в проверенных учётных записях поля Department, Title, Company и Office пустые.

## Разделение ответственности

1. Python-сборщик получает карточки компьютеров, ноутбуков и мониторов из OCS.
2. PowerShell с модулем ActiveDirectory получает сведения AD по короткому логину пользователя.
3. Сборщик объединяет результаты в нормализованные записи и передаёт их в API приложения.
4. Backend сопоставляет карточки, создаёт недостающие записи и закрепляет оборудование.

Backend самостоятельно не подключается к OCS или AD. Пароли OCS, AD и MySQL в запрос импорта не передаются.

## Изменения обычного API

- Сотрудник: `ad_login`, `ad_domain`, `ad_guid` доступны при создании, редактировании и чтении.
- Поиск: `GET /api/employees?ad_login=m.shutov&ad_domain=ruskon.local`.
- Логин хранится без домена, в нижнем регистре; пустое значение допустимо для ручных карточек.
- Заполненная пара домен + логин уникальна. GUID также уникален. Нормализация UUID и логинов выполняется сервером.
- `POST /api/warehouse/items` и `POST /api/workplaces` допускают отсутствие `branch_id`.
- Если задан `department_id`, необходимо указать соответствующий существующий филиал.
- У оборудования без филиала и явно заданного размещения местонахождение — «Не определено».
- Инвентарный номер поштучного оборудования выдаётся приложением в общей последовательности.
- Характеристики оборудования дополнены полями `os_name` и `os_version`.
- Названия рабочих мест без филиала уникальны без учёта регистра, включая кириллицу.

Филиал и отдел можно заполнить позднее через обычный API.

## Пакетный импорт

`POST /api/integrations/ocs-ad/import`

Пример нормализованного запроса (значения оборудования демонстрационные):

```json
{
  "source": "ocs",
  "source_key": "main",
  "dry_run": true,
  "max_age_days": 30,
  "records": [
    {
      "ocs_id": 94,
      "computer_name": "WS-TEST-01",
      "last_inventory_at": "2026-10-05T11:00:00+04:00",
      "domain": "ruskon.local",
      "ad_login": "m.shutov",
      "ad_guid": "3dc0fec6-9dfa-40dd-b115-cf6eaa9b4642",
      "full_name": "Шутов Максим",
      "ad_enabled": true,
      "computer": {
        "form_factor": "desktop",
        "manufacturer": "Acer",
        "model": "Aspire XC-1660",
        "serial_number": "EXAMPLE-PC-001",
        "ram_gb": 4,
        "processor": "Intel Core i3-10105",
        "os_name": "Windows 11 Pro",
        "os_version": "10.0.26200",
        "ip_address": "172.16.55.197",
        "mac_address": "1C:69:7A:9E:C7:AC"
      },
      "monitors": [
        {
          "ocs_id": 72,
          "name": "S24D300",
          "manufacturer": "Samsung",
          "model": "S24D300",
          "serial_number": "EXAMPLE-MON-001"
        }
      ]
    }
  ]
}
```

`last_inventory_at` должен содержать часовой пояс. В примере дату необходимо заменить актуальной при проверке. Часовой пояс исходной даты OCS задаётся в настройках будущего сборщика; его нельзя автоматически считать часовым поясом компьютера сборщика. В backend дата сохраняется в UTC.

До 500 записей в одном пакете, до 20 мониторов у компьютера. Неизвестные поля отклоняются с 422, чтобы ошибки контракта не теряли данные молча.

`source_key` — постоянный идентификатор экземпляра OCS, например `main`. Не менять его между запусками. ID компьютеров и мониторов относятся к конкретному источнику.

## Результат обработки

Ответ содержит `dry_run`, `run_id`, итоговые счётчики и `records` с результатом каждого компьютера:

- `created` — создана хотя бы одна карточка;
- `updated` — обновлены поля, установлена связь источника или выполнено закрепление;
- `unchanged` — повторный импорт не требует изменений;
- `skipped` — запись не прошла фильтрацию;
- `conflict` — запись требует разбора.

Каждый результат содержит исходный индекс, ID OCS, имя компьютера, ID сотрудника, рабочего места и оборудования, выбранную `computer_category` («Компьютеры» или «Ноутбуки»), `actions`, `warnings`, `message`. Для пропущенной или конфликтной строки категория может отсутствовать.

Счётчики: `employees_created`, `employees_updated`, `workplaces_created`, `computers_created`, `computers_updated`, `monitors_created`, `monitors_updated`, `assets_assigned`, `warnings`, `conflicts`, `skipped`, `unchanged`.

Счётчики `computers_created` и `computers_updated` включают и стационарные компьютеры, и ноутбуки. Связь с OCS для обоих использует вид `computer`, поэтому смена названия не создаёт другую связь источника.

`warnings` — количество сообщений предупреждения, а не число компьютеров. Действия `source_linked` и `workplace_employee_assigned` возвращаются в строках отчёта.

## Правила сопоставления

### Сотрудник

1. Поиск по нормализованным домену и логину AD.
2. Карточку с таким логином без домена можно дополнить подтверждённым доменом.
3. GUID позволяет найти прежнюю карточку после смены логина.
4. Если логин и GUID указывают на разных людей, вернуть конфликт.
5. Если найдена ручная карточка без логина с совпадающими именем или email, не объединять её автоматически: вернуть кандидатов.
6. Для подтверждённого сопоставления можно передать `employee_id` либо заранее заполнить логин через API сотрудников.
7. Отключённые учётные записи AD пропускаются. Неактивный сотрудник приложения автоматически не активируется.

Имя берётся из DisplayName. Отчество не выдумывается. Должность, email и телефон необязательны.

### Компьютер и ноутбук

`computer.form_factor` — необязательное поле: `desktop` выбирает «Компьютеры», `laptop` выбирает существующую категорию «Ноутбуки». Явный тип имеет приоритет перед именем.

Если тип не передан, ноутбуками считаются подтверждённые пользователем имена без учёта регистра:

`Notebook-RTI`, `NOTEBOOK-CHPU-DISP`, `LAPTOP-COM`, `NOTE-PROXIMA-1`, `NOTE-BUH-2`, `NOTE-HR-1`, `UP-OP-NOTES1`, `NOTE-WED-1`, `Notebook-sar1`, `Ershov-Note`.

Список можно заменить переменной `OCS_AD_LAPTOP_NAMES` (имена через запятую). При отсутствии переменной используется список выше, пустая переменная отключает сопоставление по именам. Произвольные имена с похожими префиксами автоматически не считаются ноутбуками.

Для прочих имён без явного типа сохраняется категория найденной карточки; новое устройство создаётся как «Компьютеры». Поэтому переименование уже связанного ноутбука само по себе не превращает его в стационарный ПК. Ноутбуки имеют поштучный учёт и закрепляются за рабочим местом с теми же правилами, что ПК; характеристики, сеть, мониторы и необязательный филиал поддерживаются одинаково.

1. Поиск по сохранённой связи источник + ID OCS.
2. При отсутствии связи — поиск по достоверному серийному номеру в обеих категориях «Компьютеры» и «Ноутбуки», чтобы не создать дубль при неверной классификации.
3. Заглушки, включая `Default string`, `Unknown`, `System Serial Number`, не считаются серийным номером.
4. При совпадении только имени существующей карточки требуется явное `computer.item_id`.
5. Если совпадения отсутствуют, создать поштучное оборудование без обязательного филиала.
6. При смене ID OCS достоверный серийный номер может связать новую запись источника с существующим компьютером.
7. Несколько совпадений, архивная карточка или несовпадение достоверных серийных номеров — конфликт.
8. Если подтверждённый тип отличается от категории существующей карточки, вернуть конфликт. Сначала проверить тип и исправить категорию вручную; импорт не переклассифицирует ручные карточки.

### Монитор

Мониторы создаются отдельными единицами категории «Мониторы» и закрепляются за тем же рабочим местом, что компьютер.

- Сначала поиск по сохранённой связи источника и ID записи монитора, затем по достоверному серийному номеру.
- Одинаковая модель не является признаком одного физического монитора.
- Новая запись без достоверного серийного номера пропускается с предупреждением.
- Для такого монитора можно заранее создать карточку через обычный API и передать её `monitors[].item_id`.
- Уже сохранённая связь OCS позволяет повторно обработать монитор даже при пустом серийном номере.
- Связь с ID записи OCS не заменяет физический серийный номер. После изменения ID неоднозначное сопоставление требует ручного решения.

В проверенных карточках OCS встречались мониторы как с серийным номером, так и без него.

### Рабочее место и закрепление

- Сначала используется сохранённая связь компьютера или его действующее закрепление.
- Для первоначального сопоставления используется нормализованное имя компьютера.
- Новое рабочее место может не иметь филиала и отдела.
- Переименование компьютера не создаёт второе рабочее место; сохранённое название рабочего места не перезаписывается.
- Сохраняется существующее ограничение: сотрудник закрепляется за одним рабочим местом.
- Оборудование, установленное на другом рабочем месте, автоматически не перемещается.
- Смена пользователя у уже занятого рабочего места — конфликт.
- Повторные компьютер, логин или монитор внутри одного пакета дают конфликт для всех неоднозначных строк.
- Отсутствие оборудования в следующем снимке не снимает его с рабочего места.

## Обновления и фильтрация

Поля, принятые от источника, отслеживаются отдельно от ручных исправлений. Последующий импорт обновляет их, только если текущее значение совпадает с предыдущим значением источника или пустое. Ручная правка сохраняется с предупреждением. Пустые поля источника ничего не стирают.

При повторном импорте филиалы и отделы не меняются автоматически. Неизвестное местоположение не стирает уже заполненное.

По умолчанию пропускаются инвентаризации старше 30 дней; порог задаётся `max_age_days`. Снимок старее уже обработанного также пропускается. Дата более чем на пять минут в будущем требует проверки времени источника.

Записи без подтверждённых логина, домена, имени и состояния AD пропускаются. Исключённые логины задаются переменной `OCS_AD_EXCLUDED_LOGINS`, через запятую; по умолчанию `administrator,admin`.

## Транзакции и проверка

- `dry_run: true` используется по умолчанию: выполняет те же проверки и построение связей, затем откатывает всю транзакцию.
- Проверка не сохраняет карточки, движения, закрепления, события и журнал запуска.
- ID в предварительном отчёте являются предполагаемыми и могут отличаться при последующем применении.
- `dry_run: false` применяет допустимые строки.
- Одна строка обрабатывается в отдельной транзакционной точке сохранения: конфликт откатывает сотрудника, компьютер, мониторы, рабочее место и историю этой строки.
- Пропущенный монитор без серийного номера является предупреждением; компьютер и сотрудник могут быть импортированы.
- Конфликт одной строки не отменяет остальные допустимые строки.
- Инвентарные номера резервируются под существующей блокировкой приложения.
- При применении все совпадения проверяются заново, независимо от предварительного отчёта.

## Авторизация и журнал

Импорт доступен администратору с JWT либо по отдельному Bearer-токену из `OCS_AD_IMPORT_TOKEN`. При пустой переменной сервисный токен отключён. Токен интеграции принимается только маршрутами импорта и чтения его отчёта; обычный API сотрудников и оборудования его не принимает.

Настройки добавлены в `.env.example`. Токен должен быть случайным отдельным секретом; не помещать его в исходный код или журналы. Передавать по защищённому каналу либо в ограниченной внутренней сети.

Применённый запуск сохраняется в `ocs_import_runs`. Отчёт доступен по:

`GET /api/integrations/ocs-ad/runs/{run_id}`

Создание оборудования, обновления и закрепления также попадают в существующую историю оборудования с автором импорта. Время закрепления — дата импорта в UTC, а не предполагаемая дата фактической выдачи пользователю.

## Миграция и проверки

При запуске backend существующим таблицам добавляются поля AD, ОС и нормализованного имени рабочего места. Создаются таблицы связей OCS и отчётов. Старые сотрудники без логинов сохраняются. Повторный запуск миграции допустим.

Перед запуском на рабочей базе сохранить её резервную копию. При старых рабочих местах без филиала с одинаковыми именами без учёта регистра сначала устранить дубли: новый уникальный индекс не допускает их.

Тесты покрывают режим проверки без изменений БД, повторный импорт, мониторы без серийника, явное сопоставление, конфликты владельцев, частичный успех пакета, ручные правки, смену логина, миграцию существующей БД и ограничения токена.

## Сборщик

Сборщик `tools/ocs_ad/collector.py` преобразует реальные поля OCS:

- `hardware.NAME` → `computer_name`;
- подтверждённые имена ноутбуков и `bios.TYPE` → `computer.form_factor`;
- `hardware.USERID` → запрос AD по логину;
- подтверждённый домен → `domain`, не полагаться на пустой USERDOMAIN;
- `bios.SSN` → серийный номер ПК;
- `bios.SMANUFACTURER / SMODEL` → производитель и модель ПК;
- `monitors.ID / CAPTION / MANUFACTURER / SERIAL` → записи мониторов;
- память, накопители и сеть → характеристики с проверкой единиц и выбора адаптера;
- `hardware.LASTDATE` → дата с явно заданным часовым поясом;
- результат AD → логин, GUID, имя, состояние и необязательные контактные поля.

Сборщик не должен передавать весь ответ OCS: служебные секции и ключи лицензий для импорта не нужны.

Перед первым применением проверить часовой пояс `LASTDATE`, результаты AD и отчёт `dry_run`. Дубли сотрудников и оборудования проверяются по всему запуску до разбиения на пакеты. Мониторы без серийника по-прежнему требуют ручного сопоставления. Для первого запуска без обращения к приложению доступен `--collect-only`.
