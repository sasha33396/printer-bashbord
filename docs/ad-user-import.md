# Импорт сотрудников и рабочих мест из Active Directory

## Статус

Запланировано. Реализация пока не начата.

## Цель

Создать PowerShell-скрипт, который запускается на администраторском компьютере с доступом к Active Directory, читает XML-файл сетевого сканирования, получает сведения о пользователях из AD и через API приложения:

- создаёт или обновляет сотрудников;
- создаёт рабочие места по именам компьютеров;
- закрепляет сотрудников за рабочими местами;
- находит уже заведённые компьютеры на складе по наименованию;
- закрепляет найденные компьютеры за соответствующими рабочими местами;
- возвращает отчёт о созданных записях, обновлениях, пропусках и конфликтах.

Повторный запуск с теми же данными не должен создавать дубли.

## Источник данных

Скрипт получает XML-файл со строками следующего вида:

```xml
<row
  status="alive"
  name="WS-TEST-11"
  os_version="Windows"
  ip="192.168.0.116"
  manufacturer="GIGA-BYTE TECHNOLOGY CO.,LTD."
  mac="74:D4:35:F4:19:D4"
  user="RUSKON\g.petrova"
  has_http="0"
  is_http8080="0"
  has_https="0"
  has_ftp="0"
  has_rdp="0"
  sIsDNSScan="0"
  expanded="0"
>
  <share name="Scan"/>
  <share name="Users"/>
  <radmin port="4899 (v3 Windows Authentication)"/>
</row>
```

Используемые атрибуты:

| Атрибут | Назначение |
|---|---|
| `name` | Наименование компьютера и рабочего места |
| `user` | Домен и логин пользователя |
| `status` | Доступность компьютера при сканировании |
| `ip` | IP-адрес компьютера |
| `manufacturer` | Производитель, используется для дополнительной проверки |
| `mac` | MAC-адрес, в будущем может стать устойчивым идентификатором компьютера |
| `os_version` | Операционная система |

Вложенные сведения о сетевых папках и службах на первом этапе не используются.

## Предварительная фильтрация

PowerShell-скрипт должен пропускать строки, в которых:

- отсутствует имя компьютера;
- отсутствует пользователь;
- поле `user` не соответствует формату `ДОМЕН\логин`;
- пользователь входит в настраиваемый список служебных учётных записей;
- имя компьютера не соответствует разрешённым шаблонам, если такой фильтр включён.

При необходимости можно обрабатывать только записи со `status="alive"`. Пропущенные строки должны попадать в отчёт с указанием причины.

## Получение пользователя из AD

Из значения `RUSKON\g.petrova` извлекаются:

- домен: `RUSKON`;
- логин: `g.petrova`.

Основной поиск выполняется по `SamAccountName`. У пользователя необходимо запросить:

- `SamAccountName`;
- `DisplayName`;
- `Department`;
- `Title`;
- `Mail`;
- `Enabled`.

Пример логики поиска:

```powershell
$domainLogin = "RUSKON\g.petrova"
$login = ($domainLogin -split '\\')[-1]

$user = Get-ADUser `
    -Filter "SamAccountName -eq '$login'" `
    -Properties DisplayName, Department, Title, Mail, Enabled
```

`UserPrincipalName` не следует сравнивать с коротким логином: обычно он имеет вид `g.petrova@domain.local`.

## Изменения модели сотрудников

Сотруднику требуется отдельное поле `ad_login`:

- хранит нормализованный `SamAccountName` без имени домена;
- сравнивается без учёта регистра;
- должно быть уникальным для заполненных значений;
- используется как основной ключ повторного импорта.

ФИО нельзя использовать как уникальный ключ из-за однофамильцев и возможной смены фамилии.

В примечание сотрудника можно добавлять текст:

```text
Автоматический импорт. Компьютер: WS-TEST-11
```

Имя компьютера также должно храниться через связь сотрудника с рабочим местом, поэтому примечание является только дополнительной информацией.

## Передача данных в приложение

Рекомендуется один пакетный запрос вместо отдельных запросов на создание сотрудника, рабочего места и связи:

```text
POST /api/integrations/ad-workplaces/import
```

Пример тела запроса:

```json
{
  "source": "network_scan",
  "dry_run": true,
  "records": [
    {
      "computer_name": "WS-TEST-11",
      "ip_address": "192.168.0.116",
      "mac_address": "74:D4:35:F4:19:D4",
      "manufacturer": "GIGA-BYTE TECHNOLOGY CO.,LTD.",
      "os_version": "Windows",
      "domain": "RUSKON",
      "ad_login": "g.petrova",
      "full_name": "Петрова Галина Сергеевна",
      "department": "Офис Краснодар",
      "position": "Специалист",
      "email": "g.petrova@example.local",
      "ad_enabled": true
    }
  ]
}
```

PowerShell отвечает за чтение XML и AD. Все правила создания, обновления и связывания записей должны находиться в backend приложения.

## Правила обработки на сервере

### Сотрудник

1. Нормализовать `ad_login`: убрать пробелы и привести к нижнему регистру.
2. Найти сотрудника по `ad_login` без учёта регистра.
3. Если сотрудник не найден — создать его.
4. Если найден — обновить разрешённые поля из AD.
5. Если пользователь отключён в AD, не удалять сотрудника автоматически. Вернуть предупреждение или применить отдельно настраиваемое правило деактивации.
6. Не перезаписывать вручную заполненные данные без явно выбранной политики синхронизации.

### Филиал и отдел

Значение `Department` из AD необходимо сопоставлять со справочником приложения через отдельную таблицу соответствий. Нельзя автоматически создавать отдел при любом неизвестном значении AD без проверки.

Пример соответствия:

```text
AD: OPM Krasnodar  →  филиал: ОП Краснодар, отдел: ОМТС
```

Если соответствие не найдено, сотрудник может быть создан без отдела, а запись должна попасть в предупреждения.

### Рабочее место

1. Нормализовать имя компьютера: убрать пробелы и привести к верхнему регистру.
2. Найти рабочее место по нормализованному имени, например `WS-TEST-11`.
3. Если рабочего места нет — создать его.
4. Филиал и отдел рабочего места брать из сопоставленного подразделения сотрудника.
5. Закрепить сотрудника за рабочим местом.
6. Повторный импорт не должен создавать второе рабочее место или повторную связь.

Для надёжного импорта у рабочего места желательно иметь уникальное нормализованное поле с именем компьютера либо обеспечить уникальность существующего поля `name` без учёта регистра.

### Компьютер со склада

1. Искать позицию с категорией `Компьютеры` и поштучным учётом.
2. Основной критерий первого этапа — точное совпадение нормализованного `name` с `computer_name`.
3. Если компьютер найден и свободен — закрепить его за рабочим местом.
4. Если он уже закреплён за этим рабочим местом — не создавать повторную связь.
5. Если он закреплён за другим рабочим местом — вернуть конфликт и ничего автоматически не перемещать.
6. Если компьютер не найден — создать сотрудника и рабочее место без оборудования, добавив предупреждение в отчёт.

Не следует автоматически создавать складской компьютер только по XML: в нём нет обязательных инвентарного и серийного номеров, поэтому возможны дубли и неполные карточки.

В будущем поиск можно усилить с помощью MAC-адреса, серийного номера или отдельного поля сетевого имени компьютера.

## Конфликтные ситуации

Импорт не должен автоматически исправлять следующие конфликты:

- сотрудник уже закреплён за другим активным рабочим местом;
- рабочее место закреплено за другим сотрудником;
- найденный компьютер установлен на другом рабочем месте;
- одному логину соответствуют несколько сотрудников;
- одному имени компьютера соответствуют несколько складских позиций;
- отдел из AD невозможно сопоставить со справочником;
- пользователь отсутствует или отключён в AD;
- значение `user` принадлежит служебной учётной записи;
- в XML встречается один компьютер с разными пользователями.

Такие записи должны возвращаться в отчёте и обрабатываться вручную.

## Проверка перед применением

API должен поддерживать два режима:

- `dry_run: true` — проверить данные и показать план без изменений базы;
- `dry_run: false` — применить допустимые операции.

Рекомендуемый порядок работы:

1. Запустить PowerShell в режиме проверки.
2. Просмотреть сформированный отчёт.
3. Исправить сопоставления отделов и конфликтные записи.
4. Повторить проверку.
5. Запустить применение.

## Ответ API и отчёт скрипта

Ответ должен содержать итоговые счётчики и результат каждой исходной строки:

```json
{
  "dry_run": true,
  "processed": 25,
  "employees_created": 8,
  "employees_updated": 12,
  "workplaces_created": 6,
  "computers_assigned": 15,
  "warnings": 4,
  "conflicts": 2,
  "records": []
}
```

PowerShell выводит краткую сводку в консоль и сохраняет подробный отчёт в JSON или CSV:

```text
Обработано: 25
Сотрудников создано: 8
Сотрудников обновлено: 12
Рабочих мест создано: 6
Компьютеров закреплено: 15
Не найдено компьютеров на складе: 3
Пользователей не найдено в AD: 1
Конфликтов привязки: 2
```

## Авторизация и безопасность

Для интеграции нужен отдельный сервисный API-токен:

- не использовать логин и пароль администратора внутри `.ps1`;
- ограничить токен только операцией AD-импорта;
- предусмотреть отзыв и замену токена;
- не выводить токен в журнал;
- хранить его через безопасный механизм Windows или в защищённом конфигурационном файле;
- ограничить доступ к API локальной подсетью или IP администраторского компьютера.

Пока приложение работает по HTTP, сервисный токен передаётся по локальной сети без шифрования. До внедрения HTTPS следует дополнительно ограничить сетевой доступ к API.
